# Samsung Galaxy A31: initial bring-up

This is an unfinished native XNU port for SM-A315F / MT6768. It is not an
installable iOS build. No XNU kernel has been compiled or booted on the A31.
The existing Redmi instructions and `shim/build.sh` do not apply to Samsung.

## Verified on the connected phone, 2026-10-22

- SM-A315F, Android 12, A315FXXU5DXJ1; unlocked bootloader.
- TWRP 3.7.1_12-1 installed from the user's `TWRP.tar`; Odin reported PASS.
- ADB sync can read as root, although shell/exec-out runs as uid 2000.
- Two independent reads agree for boot, recovery, dtbo, vbmeta,
  vbmeta_samsung, live FDT and recovery kernel config. Backups are private
  under `research/a31-capture-1/`; no userdata or calibration partitions
  were written. The boot partition is still the original Android boot.
- CPU probe ran on all eight CPUs: Cortex-A55 (six) and Cortex-A75 (two).
  Linux exposes a filtered MMFR0 value. That value is not an EL1 measurement
  and does not establish whether a 16 KiB MMU setup works on this phone.
- Timer: 13 MHz, virtual interrupt 27. GICD 0x0c000000, GICR 0x0c040000.
- eMMC uses MediaTek MSDC, not Qualcomm UFS. Touch is on I2C6 at 0x50.
- mtkfb: visible 1080x2400, virtual 1088x4800, 32 bpp, stride 4352 bytes.
- The live `atag,videolfb` blob and reserved framebuffer region both give
  0x77720000 / 0x022e0000. The separate `atag,videolfb-fb_base_l` property
  still contains 0x7e605000. Do not use those separate properties as proof
  of the current scanout address. The panel uses command mode; copying
  pixels alone is not a validated display driver.

## Implemented source changes

`0082-a31-initial-machine-target.patch` adds MACHINE_CONFIG=A31 with plain
arm64, the shared generic CPU configuration and a default timer PPI of 27.
It selects samsung,a31 in the platform expert and omits the Redmi-specific
early framebuffer writes/mappings. Qualcomm UFS initialization returns ENXIO
for A31, preventing the UFS-dependent input and USB initialization chain.
Shared libpthread, BearSSL and HFS staging also accepts A31.

`tools/a31-collect.py` collects inputs through ADB sync and verifies binary
files with a second independent read. `tools/a31_fdt.py` parses the live FDT.
`tools/mka31adt.py` produces a CPU0/RAM-disk ADT for the A31 target; it rejects
memory outside an observed System RAM range or overlapping fixed firmware
reservations. It deliberately publishes no storage, display or input device.

An ADT was generated with RAM base 0x100000000 and size 0x3fe00000 (including
a 1 MiB panic area). This is a candidate for a minimal kernel test, not a
validated memory map for running the full iOS userland. A Samsung boot shim
and a diagnostic output path are still required before a hardware test.

## Validation performed

- Eight parser, memory-boundary and ADT tests pass with
  `python -m unittest discover -s tools -p test_a31.py -v`.
- The new kernel patch applies to the affected source files after the
  existing 0001-0081 patch series from xnu-8796.141.3.
- AArch64 compilation of the A31 timer/header configuration and disabled
  early-console helpers succeeds. The disabled console test emits only ret.
- The native CPU diagnostic was compiled using Android NDK 28.2 and executed
  on this phone in TWRP. This was a Linux userspace test, not an XNU boot.

The first full kernel build is running in GitHub Actions:
[run 39821518791](https://github.com/Dema123123c/ios-sweet/actions/runs/39821518791),
commit `62ac3e2`. Host tests and Xcode/dependency setup passed; compilation
is still in progress at this checkpoint. No full compile success or XNU
boot has been confirmed.

## GitHub Actions build

The user-owned public fork is [Dema123123c/ios-sweet](https://github.com/Dema123123c/ios-sweet).
Build source from `a31-bringup`, selecting the A31 machine explicitly:

```sh
gh workflow run xnu.yml -R Dema123123c/ios-sweet --ref a31-bringup -f machine_config=A31 -f macos_version=13.5 -f kernel_config=DEVELOPMENT
gh run list -R Dema123123c/ios-sweet --workflow xnu.yml --branch a31-bringup
```

Patch/workflow pushes to `a31-bringup` also build A31 automatically.

The workflow checks the A31 host tools, selects an installed Xcode 15 to
match the xnu-8796 IORPC ABI, and retains `xnu-build-log-A31` even after a
compile failure. Successful kernel output is in `xnu-kernel`; generated
headers and patched source are in `xnu-buildtree`. A build artifact is not
an installable Samsung boot image and does not demonstrate a hardware boot.

GitHub has announced that its macOS 14 runner image will be retired on
2026-11-02. Future runs will require a compatible Xcode 15 environment or
an explicit port of the build to a newer toolchain; do not silently switch
to Xcode 16, whose generated IORPC ABI differs.

## Remaining work

1. Build the A31 target on macOS/Xcode, using the existing xnu workflow in a
   user-owned fork, and resolve any target-specific build failures.
2. Implement the Samsung/MediaTek boot shim and an observable diagnostic
   path; validate EL1 handoff, 16 KiB translation and GIC/timer interrupts.
3. Implement eMMC/MSDC and the command-mode display path, then touch and keys.
4. Validate a minimal RAM-disk process before attempting the much larger
   iOS filesystem, dyld cache, launchd and SpringBoard.

Do not flash the Redmi shim, ADT or root image onto the A31. No A31 XNU flash
package is included. All subsequent partition writes require a separately
confirmed, concrete image and a recovery procedure.

Arm's CPU descriptions support the architectural feasibility of 16 KiB
translation: [Cortex-A55 TRM](https://documentation-service.arm.com/static/5e7e1405b471823cb9de57ae)
and [Cortex-A75 TRM](https://documentation-service.arm.com/static/5e7e09f6a3736a0d2e862e90).
They do not replace a bare-metal test of this device and firmware.
