# Samsung Galaxy A31: initial bring-up

This is an unfinished native XNU port for SM-A315F / MT6768. It is not an
installable iOS build. The A31 XNU target reaches its first C checkpoint on
the actual phone, then deliberately resets to TWRP; full kernel startup
and iOS userland have not run.
The existing Redmi instructions and `shim/build.sh` do not apply to Samsung.

## Native pmap bootstrap PASS, 2026-10-26

V24 source `0b7dee09e0314cedc28ed00126a8bc04a9b2fc2d` passed on the actual
A31. Matching pstore verifies rebound page-table pointers, pmap metadata
allocations within managed RAM, the kernel pmap root/flags/reference count
and initial ASID bitmap state. `pmap_bootstrap` returned and emitted
`PMAP-BOOTSTRAP-CHECK PASS`; the phone returned automatically to TWRP.
V24 is retained in BOOT; recovery and both vbmetas remain unchanged.
This still stops inside `arm_vm_init`, BEFORE post-pmap page-table expansion,
drivers, scheduling and userland. GPU/display and iOS have not started.
See [pmap evidence and backup scope](A31-PMAP-CHECKPOINT.md).

## Native final VM-table checkpoint PASS, 2026-10-26

V23 source `2dd5a3519740da42b2103ab97454259775abcae9` passed on the actual

- CPU probe ran on all eight CPUs: Cortex-A55 (six) and Cortex-A75 (two).
  Linux exposes a filtered MMFR0 value. That value is not an EL1 measurement

- Timer: 13 MHz, virtual interrupt 27. GICD 0x0c000000, GICR 0x0c040000.
- eMMC uses MediaTek MSDC, not Qualcomm UFS. Touch is on I2C6 at 0x50.
- mtkfb: visible 1080x2400, virtual 1088x4800, 32 bpp, stride 4352 bytes.

## Implemented source changes

`0082-a31-initial-machine-target.patch` adds MACHINE_CONFIG=A31 with plain
arm64, the shared generic CPU configuration and a default timer PPI of 27.
It selects samsung,a31 in the platform expert and omits the Redmi-specific
early framebuffer writes/mappings. Qualcomm UFS initialization returns ENXIO
for A31, preventing the UFS-dependent input and USB initialization chain.
Shared libpthread, BearSSL and HFS staging also accepts A31.

`tools/a31-collect.py` collects inputs through ADB sync and verifies binary
files with a second independent read. `tools/a31_fdt.py` parses the live FDT.
`tools/mka31adt.py` produces a CPU0/RAM-disk ADT for the A31 target; it rejects
memory outside an observed System RAM range or overlapping fixed firmware
reservations. It deliberately publishes no storage, display or input device.

An ADT was generated with RAM base 0x100000000 and size 0x3fe00000 (including
a 1 MiB panic area). This is a candidate for a minimal kernel test, not a
validated memory map for running the full iOS userland. A Samsung boot shim
and a validated diagnostic path are still required before an XNU hardware test.

## Diagnostic shim milestone

`shim/a31/` is a separate standalone diagnostic shim. It does not yet load
XNU. It checks EL1/EL2 entry, an actual 16 KiB virtual alias, GICv3 and three
virtual-timer IRQs. The native variant verifies the live MT6768 FDT and
sec-log reservation before appending Samsung's LOGM ring format. It has
no storage, display, touch or USB driver. V6 returns to matching TWRP after
logging its result through the verified software-return path.

The first orange-state tests showed a user-observed reboot loop, with TWRP
still reachable by buttons. No matching diagnostic session was recovered.
Original BOOT was restored with two complete independent matching readbacks;
both vbmetas stayed unchanged. The current source adds a second persistent
log path through the measured ECC-free ramoops console and disables the
FDT-validated MediaTek watchdog after logging its original state. V6 now
verifies native execution, translation/timer checks and log persistence.
The cause of the earlier loop remains unknown. Linux-user-mode checks and
compilation alone are not native evidence; the recovered V6 session is.
See `shim/a31/README.md` for layout and sources.

[CI 39827253373](https://github.com/Dema123123c/ios-sweet/actions/runs/39827253373)
passes 21 Python checks, C parser/log tests with ASan/UBSan, and QEMU runs
entering at EL1 and EL2. QEMU uses its own platform/UART variant; this
does not demonstrate Samsung bootloader compatibility or log persistence.

`tools/mka31diag.py` prepares a private diagnostic BOOT and an exact stock
BOOT restore package. It preserves the stock Android DT table, ramdisk,
v2/2048 header and load addresses, validates an unsigned AVB hash footer
and checks Odin tar round trips. It never writes to a phone. The AOSP
mkbootimg/avbtool scripts must match the pinned android-12.0.0_r34 hashes.
Stock components are not distributed in Git. After the first hardware
rejection, `--parent-vbmeta` is mandatory: the packager verifies the supplied
parent metadata signature and enforces its BOOT hash contract. A mismatch
removes the candidate boot.img and produces no Odin tar. Unsupported BOOT
contracts reject. Disabled verification in supplied metadata is reported
explicitly and does not establish that the phone accepts that metadata.
Signed-parent checks require OpenSSL on PATH. Four regression cases and a
full local packager rejection check cover the original hardware failure.

After physical unlock, stock Android was measured as unlocked/orange and
TWRP successfully booted again. The packager now has a separate explicit
`--unlocked-stock-properties` mode for testing unlocked AVB policy. It
requires the operator's fresh stock Android getprop JSON identifying this
exact A31/firmware, completed boot, flash.locked=0, unlocked and orange.
It still verifies the parent signature and descriptor structure/range,
records the BOOT digest mismatch, and keeps bootloader_acceptance_verified
false. The JSON is operator evidence, not hardware attestation. Default
packaging still rejects changed BOOT and removes the candidate; OEM-unlock
permission alone does not enable this mode. No vbmeta write is needed to
prepare this test, and actual Samsung acceptance remains a hardware test.
The unlocked mode additionally requires `--live-recovery-fdt`, freshly read
from the current TWRP boot. Its bootloader-supplied `/chosen/bootargs` must
contain exactly one unlocked device state and orange verified-boot state;
green or contradictory/missing values reject before producing a package.
This closes an observed gap: stock Android was unlocked/orange, but the
later recovery preceding a failed test had unlocked/green bootargs. After
the user reported unlocking again, recovery's live FDT changed to
unlocked/orange. The reason for that transition has not been established.

`tools/a31_diag_log.py` reads last_kmsg/sec_log in TWRP and accepts only
sessions for the expected build. Missing logs mean missing evidence, not
a demonstrated boot failure.

The first approved native boot attempt was rejected by the Samsung
bootloader. BOOT was written and fully read back with the intended image
hash, but the photographed error reports `Partitions boot` and a BOOT hash
mismatch. The saved parent vbmeta has flags 0 and requires the original
BOOT digest; validating the new image's own unsigned footer did not
validate that parent relationship. The original backup matches the parent
BOOT descriptor exactly; the diagnostic image does not. Do not repeat this
image under the former locked state or treat that attempt as evidence of
shim execution. A separately prepared package may test the same diagnostic
bytes only after reviewing the new measured unlocked state and recovery path.

The user also observed a recovery chain-key error and a reboot loop.
TWRP was inaccessible and no diagnostic log has been recovered. After the
user entered manual Download Mode, Odin restored only the exact original
BOOT and reported a new PASS (`boot.img`, succeed 1 / failed 0). Normal
Android boot was still blocked by a recovery/public-key error. With
separate explicit user approval, factory RECOVERY from the exact Samsung
FUS firmware A315FXXU5DXJ1 was then restored. Its SHA256_RSA4096 signature,
full payload hash and exact key match against the saved parent recovery
chain were verified before flashing; the TWRP backup remains private.
Odin's new RECOVERY transfer log reports RES OK and succeed 1 / failed 0.
Stock Android recovery subsequently opened. The user independently selected
factory reset; user data must no longer be described as preserved. The
user subsequently confirmed the initial Android setup screen. ADB and
normal Android boot were then verified after setup and USB debugging were
reenabled (`sys.boot_completed=1`). Post-restoration raw partition readback
remains unavailable on unrooted stock Android.
No agent-issued
Data, vbmeta, TEE1 or bootloader write/wipe was performed during this test
and recovery sequence. Current recovery progress belongs in `NOTES.md`.

## GitHub Actions build

The user-owned public fork is [Dema123123c/ios-sweet](https://github.com/Dema123123c/ios-sweet).
Build source from `a31-bringup`, selecting the A31 machine explicitly:

```sh
gh workflow run xnu.yml -R Dema123123c/ios-sweet --ref a31-bringup -f machine_config=A31 -f macos_version=13.5 -f kernel_config=DEVELOPMENT
gh run list -R Dema123123c/ios-sweet --workflow xnu.yml --branch a31-bringup
```

Patch/workflow pushes to `a31-bringup` also build A31 automatically.

The workflow checks the A31 host tools, selects an installed Xcode 15 to
match the xnu-8796 IORPC ABI, and retains `xnu-build-log-A31` even after a
compile failure. Successful kernel output is in `xnu-kernel`; generated
headers and patched source are in `xnu-buildtree`. A build artifact is not
an installable Samsung boot image and does not demonstrate a hardware boot.

GitHub has announced that its macOS 14 runner image will be retired on
2026-11-02. Future runs will require a compatible Xcode 15 environment or
an explicit port of the build to a newer toolchain; do not silently switch
to Xcode 16, whose generated IORPC ABI differs.
